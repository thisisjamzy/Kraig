# Dreda: Historic Transaction Backfill and Balance Reconciliation

**Status**: Enhancement to the existing Audit Report feature (`PRD-AUDIT-REPORT.md`,
`PRD-AUDIT-REPORT-DETAILED.md`). Two new capabilities, meant to work together: bulk-entering a
recurring transaction across a range of months that predate a household's real Dreda usage, and
reconciling reported real-world balances against Dreda's own ledger, with a mechanism for
explaining away the resulting gap one historic transaction at a time.
**Arch**: Same established Dreda pattern as every other PRD: Firestore subcollections under
`users/{uid}`, client-side aggregation via `runTransaction()` at write time, mobile-first single
column, no Cloud Functions (Spark plan). This PRD reuses the existing transfer mechanism (the
architecture doc's Notion migration names "Transfers" as one of the five real data sources
already migrated) and the existing wallet/balance model rather than inventing a parallel one;
confirm the live shape of the transfer write path in the repo before implementation, the same
way `PRD-BUDGET-TRANSACTIONS.md` checked its assumptions against the live repo before writing
this kind of enhancement.

---

## 0. What this PRD adds, and the one idea underneath both halves

- **Backfill** (Section 1): a household that starts using Dreda in July but has been paying
  rent since January can spread that recurring transaction across January through June in one
  action, and it counts, exactly like any transaction entered in real time.
- **Reconciliation** (Section 2): a household can report what their accounts actually hold right
  now, see the gap between that and what Dreda's ledger thinks they hold, and close that gap over
  time by attributing specific historic transactions to it.

The idea connecting them: **every transaction dated in the past, whether entered one at a time or
generated by a backfill spread, gets one extra choice at the moment it's recorded: does this
transaction explain part of the gap between what the ledger says and what's actually true, or is
it just ordinary history being filled in.** Section 2.5 is where that choice lives in the UI;
everything before it builds the mechanism the choice switches on.

## 1. Historic Transaction Backfill

### 1.1 Overview

A single recurring transaction (most often a salary or a rent payment) gets spread across a
chosen range of months, from a start month to an end month, generating one real transaction per
month in that range. Each generated transaction is a normal transaction: it affects the relevant
month's `statsMonthly` the same way `createTransactionWithAggregation` already does, and it
affects the target wallet's running `balance` field the same way any transaction does, since
Firestore's running total does not care whether a write happens today about today or today about
January.

### 1.2 Data model additions

No new collection. Two new optional fields on the existing `FirestoreTransaction` shape
(`PRD-BUDGET-TRANSACTIONS.md` Section 0):

```
{
  // ...existing transaction fields (date, categoryId, accountId, amount, direction, month, etc.)
  isHistoricBackfill: boolean       // true for every transaction created by a spread
  backfillBatchId: string | null    // shared by every occurrence from one spread action
}
```

`backfillBatchId` is what lets the household view, and if needed remove, an entire spread as one
unit (Section 1.4) rather than hunting down twelve individual rows.

### 1.3 Write logic

```
function createBackfillSpread(uid, {
  title, categoryId, accountId, amount, direction,
  startMonth, endMonth, dayOfMonth, fundFromUnjustified   // Section 2.5
}) {
  const months = enumerateMonths(startMonth, endMonth);   // capped, see 1.5
  const batchId = generateId();
  const occurrences = months.map(m => ({
    date: dateForDayInMonth(m, dayOfMonth),
    month: monthKey(m),
    amount, direction, categoryId, accountId,
    description: title,
    isHistoricBackfill: true,
    backfillBatchId: batchId
  }));
  return occurrences;   // shown as a preview (Section 1.4) before any write happens
}

function commitBackfillSpread(uid, occurrences, fundFromUnjustified) {
  for (const occ of occurrences) {
    // one runTransaction() per occurrence, same shape createTransactionWithAggregation
    // already uses; fundFromUnjustified routes through Section 2.3's wrapped write instead
    // of a plain one when the household opted in
    if (fundFromUnjustified) {
      recordTransactionExplainingUnjustifiedBalance(uid, occ);
    } else {
      createTransactionWithAggregation(uid, occ);
    }
  }
}
```

One `runTransaction()` per month, sequential, is the same shape every other write in this app
already uses; a twelve-month spread is twelve small transactions, well inside any Firestore
quota concern on the Spark plan.

### 1.5 Edge cases

- **Range cap**: a spread is capped at 36 months (3 years) per action, a deliberate limit to
  keep a single bulk write bounded and to keep a person from fat-fingering a decade-long range;
  tune this in Section 7 if it turns out too tight.
- **Category not budgeted for a historic month**: the existing "record as unplanned" escape
  hatch in `PRD-BUDGET-TRANSACTIONS.md` Section 0 already covers this without any change; a
  January nobody had budgeted for yet simply falls back to that path for every generated
  occurrence.
- **Currency**: all occurrences inherit the target account's existing default-currency handling,
  no per-occurrence override.
- **Overlap with a transaction already recorded for that period**: not detected or blocked; the
  household is trusted to know whether January's rent was already entered, consistent with the
  app's existing trust model for manual entry everywhere else.

## 2. Balance Reconciliation and the Unjustified Wallet

### 2.1 Overview and why the mechanic works the way it does

A household reports what each real account actually holds right now. Dreda already knows what
its own ledger thinks each account holds (`wallet.balance`, updated at every write). The
difference between the two totals is the gap: **money the ledger believes exists but that isn't
really there** (an unrecorded expense happened at some point), or the reverse, **money that
exists but the ledger never recorded arriving** (an unrecorded income happened). This PRD calls
the UI-facing number the **unaccounted balance** and the mechanism that tracks and closes it the
**Unjustified wallet**, matching the household's own term for the underlying mechanic.

```
gap = totalLedgerBalance - totalReportedBalance
```

- `gap > 0`: the ledger overstates reality. Unrecorded expense happened somewhere.
- `gap < 0`: the ledger understates reality. Unrecorded income happened somewhere.

The Unjustified wallet's own `balance` field is set to this gap at every reconciliation
(Section 2.3), and can be signed either way.

**Why explaining a historic expense uses a transfer, not a plain expense.** Say the gap is
2,000,000 XAF (unexplained expense) and the household remembers a 1,000,000 XAF car purchase
that was never recorded. The intuitive move, recording a plain 1,000,000 XAF expense against the
account that paid for it, would be wrong here: the account's reported real balance already
reflects that the car was bought and paid for, that dip is already baked into the 2,000,000 gap.
Recording a second, separate expense today would double-count it, pulling the wallet's ledger
balance down a second time for money that only actually left the account once. The correct move
is to first move 1,000,000 XAF **into** that wallet from the Unjustified wallet (acknowledging
"this money really was there, the ledger just never knew it"), and then immediately record the
1,000,000 XAF expense against that same wallet. The two operations net to zero on the real
wallet's balance, exactly matching the fact that its true balance never should have moved a
second time, while the Unjustified wallet's balance drops by 1,000,000 XAF, correctly shrinking
the unexplained portion of the gap from 2,000,000 to 1,000,000. Explaining an unrecorded income
works the same way in reverse (Section 2.3).

### 2.2 Data schema

**Addition to `users/{uid}/wallets/{walletId}`** (small addition to the existing wallet schema):

```
{
  // ...existing wallet fields (balance, frozenAmount, currency, etc.)
  isSystemWallet: boolean    // true only for the one Unjustified wallet
  systemType: "unjustified" | null
}
```

The Unjustified wallet is created once per user, the same way default settings and exchange
rates are seeded today (`ensureUserDoc.ts`); flagged here as a small addition to that existing
seeding function rather than a new one. Being a real wallet document means it can participate in
the app's existing transfer mechanism unchanged, rather than needing bespoke balance-moving code.
It is deliberately excluded from the Accounts screen's normal list and from the Balance Sheet's
Assets total and account-composition pie chart (Section 5), since it is not a real account
anyone can spend from.

**New collection, `users/{uid}/reconciliations/{reconciliationId}`**, one document per
reconciliation check:

```
{
  id: string
  uid: string
  performedAt: timestamp
  reportedBalances: { [walletId]: number }       // what the person entered as real balance
  ledgerBalancesAtTime: { [walletId]: number }    // wallet.balance read at the same moment
  totalGap: number                                // signed, ledger minus reported
  notes: string
}
```

This is a history, not a working value; the working value is always the Unjustified wallet's
current `balance` field, which is what changes as the household explains individual
transactions between reconciliation checks (Section 2.3). The history exists so the Audit Report
(Section 5) can chart the gap over time.

**Addition to `FirestoreTransaction`** (alongside Section 1.2's backfill fields):

```
{
  isUnjustifiedAdjustment: boolean     // true for a transaction explained against the gap
  pairedTransferId: string | null      // the transfer transaction created alongside it
}
```

### 2.3 Backend logic

**Performing a reconciliation** (sets the Unjustified wallet's balance to the freshly measured
gap; a deliberate full reset rather than an incremental adjustment, since each reconciliation is
meant to be an authoritative re-check of the truth, not a guess layered on a guess):

```
function performReconciliation(uid, reportedBalances) {
  runTransaction(async (txn) => {
    const wallets = await getRealWallets(uid);   // excludes the Unjustified wallet itself
    const ledgerBalancesAtTime = {};
    let totalLedger = 0, totalReported = 0;
    for (const w of wallets) {
      ledgerBalancesAtTime[w.id] = w.balance;
      totalLedger += w.balance;
      totalReported += reportedBalances[w.id] ?? 0;
    }
    const totalGap = totalLedger - totalReported;

    txn.update(unjustifiedWalletRef, { balance: totalGap, updatedAt: serverTimestamp() });
    txn.set(reconciliationsCollection.doc(), {
      uid, performedAt: serverTimestamp(),
      reportedBalances, ledgerBalancesAtTime, totalGap, notes: ""
    });
  });
}
```

**Explaining an unrecorded expense** (the car purchase example, Section 2.1):

```
function recordTransactionExplainingUnjustifiedBalance(uid, { amount, accountId, ...rest }) {
  runTransaction(async (txn) => {
    const transferRef = transactionsCollection.doc();
    const expenseRef = transactionsCollection.doc();

    // 1. Transfer amount FROM the Unjustified wallet INTO the real wallet
    txn.set(transferRef, {
      type: "transfer", fromWalletId: unjustifiedWalletId, toWalletId: accountId,
      amount, date: rest.date, description: `Reconciliation: ${rest.description}`,
      createdAt: serverTimestamp()
    });
    txn.update(unjustifiedWalletRef, { balance: increment(-amount) });
    txn.update(accountRef(accountId), { balance: increment(amount) });

    // 2. Record the expense against that same real wallet, same as any transaction
    txn.set(expenseRef, {
      ...rest, direction: "expense", amount,
      isUnjustifiedAdjustment: true, pairedTransferId: transferRef.id,
      createdAt: serverTimestamp()
    });
    txn.update(accountRef(accountId), { balance: increment(-amount) });
    // ...plus the existing statsMonthly update createTransactionWithAggregation already does
  });
}
```

**Explaining an unrecorded income** is the mirror image: record the income into the real wallet
first, then transfer the same amount out of that wallet and into the Unjustified wallet,
increasing the Unjustified wallet's balance back toward zero.

```
function recordIncomeExplainingUnjustifiedBalance(uid, { amount, accountId, ...rest }) {
  runTransaction(async (txn) => {
    const incomeRef = transactionsCollection.doc();
    const transferRef = transactionsCollection.doc();

    // 1. Record the income against the real wallet, same as any transaction
    txn.set(incomeRef, {
      ...rest, direction: "income", amount,
      isUnjustifiedAdjustment: true, pairedTransferId: transferRef.id,
      createdAt: serverTimestamp()
    });
    txn.update(accountRef(accountId), { balance: increment(amount) });

    // 2. Transfer that same amount FROM the real wallet INTO the Unjustified wallet
    txn.set(transferRef, {
      type: "transfer", fromWalletId: accountId, toWalletId: unjustifiedWalletId,
      amount, date: rest.date, description: `Reconciliation: ${rest.description}`,
      createdAt: serverTimestamp()
    });
    txn.update(accountRef(accountId), { balance: increment(-amount) });
    txn.update(unjustifiedWalletRef, { balance: increment(amount) });
  });
}
```

The transfer amount is always locked to the transaction's own amount; it is never independently
editable, since the entire point is to explain exactly this transaction, not some other figure.

### 2.5 Where the choice lives: the toggle on every historic transaction

Both halves of this PRD produce transactions dated in the past. Rather than build a second entry
point, one toggle is added to the existing Add Transaction screen (`PRD-BUDGET-TRANSACTIONS.md`
Section 3.4), shown only when the transaction's date is not today and the Unjustified wallet's
balance is non-zero:

```
Date: [date picker: Aug 20, 2026]

  [ ] This explains part of my unaccounted balance
      Unaccounted: 2,000,000 XAF available
```

- Left unchecked (the default): the transaction is written exactly as it is today, a plain
  historic entry, no interaction with the Unjustified wallet.
- Checked: the write routes through Section 2.3's wrapped function instead of the plain one,
  using whichever direction (expense or income) the household already picked on that screen.
- The Backfill screen (Section 1.4) exposes the same toggle once, applied to every generated
  occurrence in that spread as a single choice, rather than asking twelve times; per-occurrence
  granularity is a possible v2 refinement (Section 7).

### 2.6 Edge cases

- **Explaining more than the outstanding gap**: allowed, with a warning, the same "warn but
  permit" pattern `PRD-GOALS-DEBT.md` already uses for over-repaying a debt. The Unjustified
  wallet's balance can cross zero and flip sign; that is mathematically fine and simply means
  the household has now over-corrected, which the next reconciliation will re-measure correctly.
- **One global pool, not per-account**: the unaccounted balance is a single household-wide
  figure, matching how the household described the problem ("across all accounts"), not a
  separate figure per account. A household whose chequing account is exactly right but whose
  savings account is off by the full gap amount will not see that distinction in the headline
  number, only in the per-account breakdown available from Reconciliation History. Per-account
  unaccounted tracking is a real possible v2, flagged in Section 7 rather than built now.
  reported balances, then, remain stored per-account even though the headline number is a single
  total.
- **Reconciling while a spread or single explain is mid-flight**: no locking; last-write-wins,
  the same trust-model tradeoff already recorded elsewhere in this app for a single-user-per-
  account design.
- **Currency**: reported balances are entered in each account's own existing default currency;
  no cross-currency conversion, consistent with `PRD-ANALYTICS.md` Section 4's existing stance.

## 3. Transaction history integration

Every transaction produced by either half of this PRD, the backfilled occurrences (Section 1)
and the paired transfer-plus-expense-or-income pairs (Section 2.3), is a normal document in
`users/{uid}/transactions/{id}` and appears in the ordinary Transactions screen with no special
filtering required to see it. Two small display treatments make the origin of these rows legible
rather than confusing:

- A row with `isHistoricBackfill: true` shows a small "Backfilled" tag and, on tap, offers a
  link to its batch (Section 1.4) alongside the usual edit option.
- A row with `isUnjustifiedAdjustment: true` shows a small "Reconciliation" tag, and tapping it
  shows both halves of the pair together (the expense or income, and its linked transfer via
  `pairedTransferId`), so the household can see why a transfer they don't remember making shows
  up next to a purchase they do remember making.

## 4. Firestore rules

```
match /users/{uid}/reconciliations/{reconciliationId=**} {
  allow read: if request.auth.uid == uid;
  allow create: if request.auth.uid == uid && request.resource.data.uid == uid;
  allow update, delete: if request.auth.uid == uid && resource.data.uid == uid;
}
```

No new rule is needed for the Unjustified wallet itself, since it is a normal document under the
existing `users/{uid}/wallets/{walletId=**}` rule; `isSystemWallet` and `systemType` are just two
more fields on a document the owner can already read and write.

## 5. Integration with the Audit Report

The existing Balance Sheet section (`PRD-AUDIT-REPORT.md` Section 1.2) computes Assets from real
wallets and Net Worth as Assets minus Liabilities; the Unjustified wallet is deliberately excluded
from both, and from the account-composition pie chart, since folding a discrepancy into "what you
own" would misstate the very thing an audit report exists to surface honestly. Instead, this PRD
adds a labeled call-out directly beneath the existing Net Worth calculation:

```
NET WORTH:                -1,500,000 XAF

Unaccounted (pending reconciliation):    +2,000,000 XAF
  Your real balances may run lower than the figures above
  by this amount, until explained. [Go to Reconciliation]
```

A new tenth report section, **Reconciliation and Unaccounted Balance**, is added alongside the
existing nine (`PRD-AUDIT-REPORT.md`'s own summary table), built entirely from data this PRD
already writes:

```
[Reconciliation and Unaccounted Balance]

  Unaccounted balance trend (line chart)
    X-axis: reconciliation date, Y-axis: gap, from the
    reconciliations history (Section 2.2). A line trending
    toward zero is the household closing the gap over time.

  Per-account reconciliation table
    Account | Ledger | Reported | Difference, from the most
    recent reconciliation's reportedBalances/ledgerBalancesAtTime

  Explained transactions (table)
    Date | Description | Amount | Type, every transaction
    with isUnjustifiedAdjustment: true, newest first

  Backfilled transactions (table)
    Batch | Range | Count | Total, one row per backfillBatchId
    (Section 1.4), so a full audit trail of retroactively
    entered history is visible in the same report that already
    audits everything else
```

This slots in as the tenth entry in `PRD-AUDIT-REPORT.md`'s own summary table without disturbing
the existing nine; no other section of that PRD needs to change.

## 6. Not in scope (deferred)

- Per-account unaccounted balance tracking (Section 2.6); v1 is a single household-wide figure.
- Per-occurrence explain toggling within one backfill spread (Section 2.5); v1 applies the choice
  once to the whole spread.
- Automatic suggestions for which historic transaction might explain a given gap (pattern
  matching against merchant names, typical amounts, and so on); v1 relies entirely on the
  household's own memory of what happened.
- Reversing a single explained transaction back into a plain one (or vice versa) after the fact;
  v1 requires deleting and re-entering it with the toggle set correctly.
- Multi-currency reconciliation (converting reported balances across currencies into one total).

## 7. Open decisions (confirm before or during build)

1. **Where "Manage backfill batches" and "Reconciliation" live in the navigation.** Both are
   secondary screens with no natural bottom-nav slot; tucking them behind the Audit Report's own
   entry point (since this PRD is framed as an enhancement to that feature) is the simplest
   option, matching how other secondary screens in this app already live behind an existing
   entry point rather than getting new nav real estate.
2. **Backfill range cap**: 36 months assumed in Section 1.5, worth tuning against a real
   household's actual gap in usage history.
3. **Per-account unaccounted tracking** (Section 2.6): confirmed as out of scope for v1, worth
   revisiting if a household's accounts diverge in ways the single global figure hides.
4. **Whether the transfer mechanic's audit-facing transactions should be hideable** from the
   ordinary Transactions screen behind a filter, once real usage shows whether the "Reconciliation"
   tag (Section 3) is enough, or whether the extra rows feel noisy in a long transaction history.
